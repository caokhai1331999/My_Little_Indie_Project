Atomic Operation. :: This one is multi-threading
       - One method to ensure this is the interclocked operation. It work on cpu
       level rather than the app's one. Cause it very fast
       - We have to know these fundamentals to go further:
            . Core include many units: instruction decoding, arithmatic logical
                                unit, memory unit. OS can usually assign 1
                                thread per core, But if the core is
                                hyperthreading one, we can assign more than more
                                thread for that one.            
            . CPU state: + Process : ++ Many Threads each contain :
                                     ++ Memory Mapping: in virtuall memory page:
                                        * Registry, memory, TCD, ...
                         + Thread:   ++ Assembly instruction for CPU:
                                        Appear physically in the hardware, can
                                        be executed concurrently.
                         + Fiber(not in use so just for fully infor):
                                     ++ Manual version of thread, we can save
                                        the CPU state on them. But we can't
                                        execute them concurrently.
            . "Processor" type: .. Out of order: ex: win x64: big window,
                                   can grab many instructions.-> drastically less
                                   hyperthreading cause it can use stuff in the
                                   same thread much more efficiently. 
                                .. In of order: This type execute instructions
                                   one by one, stall more often and need more
                                   hyperthreading.
            . OS's interrupts: when our game is running, os come in instead of
            let the code running on the cpu core. It save them state. Do
            other work on that core, and then execute our game's assem
            instruction/thread on other core.
            . Preemption: or Preemptive Multitasking OS in OS: Don't interrupt,
            have something called Yield() to execute our game's thread. Can be
            dissappeared if our asm is bad written. More efficient.
       - M.E.S.I(Modified.Exclusive.Shared.Invalid)(4 flags) protocol: JOB: To
       ensure cache line coherence among cores. -> that mean to ensure the core
       won't unexpectedly overwrite the same memory's location in app running
       realtime.
       For ex: core1 write to memory location 0x100 from 0 -> 4 then core4 have
       to take the that same memory location value as 4.

       - Ticking Taking: Is the process to ensure when we access a particular
       piece of data/adress. we are the only person who are doing that.
             .. Then, we have something call mutex(mutual exclusion) Thing is
             the mutex basic loop can cause the latency cause it
       doesn't know all the threads which can come in to take the memory part
       - Casey came up with an idea name mutex_ticket. which is distribute the
       tickets to all of the thread there are with unique number. Then do a loop
       through the ticket every that the thread hold which give the order of
       their turn to come.

       - So Atomic Operation: is the operation that is not switch/swap or
       interrupt while running. But how to implemeting it??? 
       - InterClock vs Mutex : . InterClock is based on MESI protocol which prevent
   cache of more than one core own the same memory location simultaneously.
                           . Mutex is a programmed structure built above the
   system, it works like an owning mark of every memory location, for every
   app/piece of code that concurrently running. If one app open first and
   already take a memory location to use, the mutex mark that is is owned and
   the other app have to get in line and wait for turn to use that memory location.
